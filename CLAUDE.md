# CLAUDE.md

## What this is

The "U.S. Scientific" keyboard layout (successor of the macOS-only "U.S. International - Scientific", github.com/goerz/USScientific.bundle). `layout.toml` is the single source of the layout; the `layoutgen` package (`src/layoutgen/`, run with `uv run layoutgen`) generates everything else. Never edit generated files by hand.

## layout.toml

The format is documented in the comment at its top. Key points: `[alternative]` (Option on macOS, AltGr on Windows/Linux) and the `[dead.<id>.map]` tables are keyed by the character a key types without that modifier (`q`, `Q` = Shift, `"1"`, `"!"`); dead keys declare their trigger with `key`; `[notes]` (keyed by character) are descriptions for the README; a dead key with `table = true` gets a table of its entries in the README, described by `[dead.<id>.notes]` (keyed by result), then `[notes]`, then the Unicode name; a dead key's `readme` is a paragraph for its README section. Characters that break the text (combining marks at the start of a string, invisible spaces) are written as `\uXXXX` with the Unicode name in a comment behind the line; everything else is literal.

Derived, not written in the TOML: the plain and Shift layers (US), Caps Lock (Shift for letters, also on the alternative layer when Shift+alternative is the uppercase form), dead key + Space = the dead key's symbol, and platform conventions for the ISO key (`§ ±` on macOS, `\ |` elsewhere; see `keys.py`).

## layoutgen

- `keys.py`: physical keys with their macOS, Keyman, Windows, and XKB codes and diagram positions.
- `model.py`: loads and validates `layout.toml`; `Layout.binding(key, layer, platform)` is what all generators use (layers include the derived `caps` and `caps-option`).
- `macos.py`: `.keylayout` and the `.bundle` (its `Info.plist` keys the layout info as `KLInfo_<layout name>`; keyed otherwise, macOS ignores the declared input source ID).
  The `.keylayout` is filled into `templates/macos.keylayout`, which holds the non-character keys, Command/Control layers, and JIS key maps.
- `keyman.py`: `.kmn` and `.kps`. `windows.py`: native layout DLL source against `kbd.h` plus scripts from `templates/windows/` (CRLF, see `.gitattributes`; `@@DLL@@`/`@@NAME@@` placeholders). Native Windows dead keys can't produce non-BMP characters; those are dropped and reported.
- `linux.py`: XKB symbols file (alternative layer on AltGr), Compose file for the dead keys, `evdev.xml` registry entry, and `templates/linux/` (`install.py`, `README.txt`; `@@ID@@`/`@@NAME@@`). XKB can't define dead keys, so each dead key types a predefined `dead_*` keysym (`dead_<id>` if it exists, else from `DEAD_POOL`, chosen to not start longer sequences in the system Compose table) and every following key gets a Compose sequence. Key types come from xkeyboard-config's `types/extra`, picked per key by simulating Caps Lock. Keysyms use X11 names where they exist, from `keysyms.txt` (vendored, regenerate with `tools/update-keysyms.py` from xorgproto's `keysymdef.h`), because GTK and IBus only match Compose sequences in 16 bits; sequences with non-BMP keys are left out. Empty levels are `VoidSymbol` (`NoSymbol` would keep `pc`'s symbols).
- `svg.py`, `docs.py`, `cheatsheet.py`: keyboard diagrams, the generated README sections (between `<!-- BEGIN/END generated: NAME -->` markers), and the PDF cheat sheet. The diagrams draw all text as glyph outlines from JuliaMono (`fonts/JuliaMono-Regular.ttf`, downloaded and checksum-verified by `make fonts`, gitignored); combining marks are placed at the preceding character's position, since there's no text shaping. A character missing from the font is an error.
  The cheat sheet must fit on one sheet printed double-sided (two letter pages): it uses compact diagrams (`compact=True`, no title line), six per page (4.6 in wide, so they fit the page height), with each description in a column beside its diagram.

## Make

- `make` (or `make help`) lists the targets, from the `## ` comments on their rule lines; give every user-facing target one. `make all` builds into `build/`: `make macos` (bundle + zip), `make keyman` (needs `npx @keymanapp/kmc` and ImageMagick), `make windows` (source and scripts in `build/us_scientific-windows/`; compiling needs Windows/MSVC, so only CI makes `us_scientific-windows.zip`, with the DLLs), `make linux` (zipped folder with `install.py`), `make cheatsheet` (rsvg-convert + LuaLaTeX).
- `make install`/`make uninstall` branch on `uname`: macOS copies the bundle to `MACOS_LAYOUTS` (default `~/Library/Keyboard Layouts`; with `SYSTEM=1`, `/Library/Keyboard Layouts` via `sudo` for the copy only, removing the per-user copy) and runs `tools/macos-activate.swift`, which registers it with `TISRegisterInputSource` (only if macOS doesn't list it yet: each registration adds a duplicate entry for the session) and enables it without a logout (a replaced bundle still needs a logout to load), Linux runs `install.py` from `make linux` (per user: `~/.config/xkb`, `~/.config/us_scientific/Compose` included from `~/.XCompose`, GNOME input source), anything else prints the Windows steps. `make install-keyman`/`uninstall-keyman` use Keyman for Linux's `km-package-install` instead.
- `make docs` regenerates the README sections and `docs/*.svg`, which are committed so GitHub shows them.
- `make test`: the tests read the generated `.keylayout` back and simulate the Keyman rules, the Windows tables, and the XKB symbols and Compose file, checking every key, layer, and dead key against `layout.toml`; they also run `install.py` against a temporary home and fail if the README or diagrams are stale (fix with `make docs`). `tests/test_linux_xkbcommon.py` loads the Linux layout into the real libxkbcommon via ctypes (skipped where libxkbcommon or xkeyboard-config is missing, as on macOS). `tests/test_windows_installed.py` checks the layout that `install.ps1` installed through `LoadKeyboardLayout`/`ToUnicodeEx`, with `test_windows.py`'s expectations (skipped except on Windows; `REQUIRE_INSTALLED_LAYOUT=1` makes that a failure).

## CI and releases

`.github/workflows/ci.yml` runs the tests (Ubuntu, with libxkbcommon), builds every release file on the platform that can (macOS: bundle, `.kmp`; Ubuntu: Linux zip, cheat sheet; Windows: compiles, zips, installs, tests, uninstalls the native layout), and uploads each as an unzipped artifact (`archive: false`; `gh run download` can't fetch those, the browser can). Actions are pinned to tags that exist: `setup-uv` only publishes full versions (`v10.3.3`). The `release` job collects the files and notes on every run; for a tag `vX.Y.Z` it creates a draft release with them (or replaces the files of an existing release). The notes are the downloads list in `tools/release-notes.py` plus the version's section of `CHANGELOG.md` (Keep a Changelog 1.1.0; add user-facing changes under `[Unreleased]`).

Versions between releases (rules at the top of `CHANGELOG.md`): after releasing `X.Y.Z`, set `version` in `layout.toml` and `pyproject.toml` to `X.Y.Z+dev` (and `uv lock`); when a change goes under `[Unreleased]`, set both to the version it implies by the Semantic Versioning rules, with `-dev`, unless they already are at least that. `Layout.numeric_version` drops the suffix for the platforms that only take numbers.

To release: change `version` in `layout.toml` (everything else follows it) and in `pyproject.toml` from `X.Y.Z-dev` to `X.Y.Z` (and `uv lock`), rename `[Unreleased]` in `CHANGELOG.md` to `[X.Y.Z] - date` (with a new empty `[Unreleased]` and the compare links at the bottom), commit, push, and push the tag `vX.Y.Z`; then review and publish the draft release, and commit `X.Y.Z+dev`.
